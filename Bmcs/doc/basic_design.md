# 基本設計書

## 1. システム概要
野球チーム・スコア管理システム (Bmcs)
チームの管理、メンバーの管理、試合のスコア入力、成績集計を行うWebアプリケーション。
ASP.NET Core Razor Pagesを使用し、Entity Framework Coreによるデータアクセスを行う。
メール送信はMailKit経由のSMTPを使用する（設定は `EmailSettings`）。

## 4. 認証・セッションの現状と課題

### 4.1 現状（`Program.cs`）
```csharp
builder.Services.AddDistributedMemoryCache();          // セッションの保存先はメモリ
builder.Services.AddSession(options =>
{
    options.IdleTimeout = TimeSpan.FromHours(1);        // 1時間操作しないと失効
    options.Cookie.HttpOnly = true;
    options.Cookie.IsEssential = true;                  // MaxAge未指定＝ブラウザを閉じると失効
});
```

ASP.NET Core の認証機構（Cookie Authentication）は使用しておらず、
**ログイン状態はセッション変数（`SessionConstant.UserAccountID` など）で保持している。**

### 4.2 これによって起きること

| 事象 | 影響 |
| --- | --- |
| **アプリを再起動すると全員がログアウトする** | セッションがメモリ保持のため。**デプロイのたびに、スコア入力中のユーザが強制ログアウトされる**。Azure App Service の再起動（デプロイ・スケール・プラットフォーム保守）でも同じ |
| 1時間操作しないとログアウトする | 試合の待ち時間や試合間の休憩で失効し得る |
| ブラウザを閉じるとログアウトする | 毎回ログインが必要。スマートフォンでの利用では負担が大きい |
| `GET /`（ログイン画面）でセッションが破棄される | ブラウザのプリフェッチやウイルス対策ソフトのURLスキャンが `/` を踏むと、意図せずログアウトする（実際に検証中に発生した） |

### 4.3 課題（未実装）

**ログイン状態の維持**を実装する。段階を分けると以下のとおり。

| 段階 | 内容 | 効果 | 規模 |
| --- | --- | --- | --- |
| 1 | セッションの保存先をメモリから**SQL Server**へ変更（`AddDistributedSqlServerCache`） | **デプロイや再起動でログアウトしなくなる**。既存コードの変更は不要 | **対応済み**（`SessionCache` テーブル） |
| 2 | `IdleTimeout` の延長と、セッションCookieに `MaxAge` を設定 | ブラウザを閉じてもログインが維持される | 小 |
| 3 | 「ログイン状態を保持する」チェックボックスと専用トークン | 明示的な同意のうえで長期間維持する | 中 |
| 4 | ログアウトをPOSTに変更し、`GET /` でのセッション破棄をやめる | 意図しないログアウトを防ぐ | 小（挙動変更のため要判断） |

**段階3の注意点**：トークンは `ResetToken` と同様に
- DBへはハッシュ化して保存する（平文保存はしない）
- 使用のたびにローテーションする
- パスワード変更時に失効させる

としないと、Cookieの盗用でアカウントが継続的に乗っ取られる。
現状「推測可能なチームパスワードが41件」あることも踏まえ、**長期間の維持は段階1・2を終えてから**とする。

## 5. 未使用データの整理

### 5.1 保持している情報
`UserAccount.LastLoginDatetime` / `Team.LastLoginDatetime` を追加した（2026-09-22）。

- ログイン成功時に、ユーザと**その所属チームの両方**を更新する
  （チーム側にも持たせることで、所属ユーザを1人ずつ調べずに未使用チームを抽出できる）
- 保存に失敗してもログインは継続する（記録のためにログインを妨げない）
- **本項目の追加以前のデータは、関連データの更新日時から推定した値**を設定している
  （移行SQL `20260922_session_lastlogin.sql`）。実際のログイン日時ではない点に注意

### 5.2 整理したい理由
公開チーム一覧・公開チーム成績は**未ログインでも閲覧できる**ため、
試し打ちで作られた不適切なデータが、新規訪問者の最初の印象になり得る。
これは離脱に直結する。

### 5.3 段階を分ける（可逆なものから）

| 段階 | 内容 | 可逆性 | 事前告知 |
| --- | --- | --- | --- |
| A | **一定期間未使用の公開チームを非公開に戻す** | 可逆（フラグのみ） | 規約への記載 |
| B | 管理画面から個別に非公開化・削除できるようにする | 可逆（論理削除） | 不要（運営操作） |
| C | 一定期間未使用のデータを**論理削除**する | 復元可能 | **必要** |
| D | 論理削除から一定期間経過したデータを物理削除する | 不可逆 | **必要** |

**段階Aを先に行うことを推奨する。** 理由は、
- 目的（公開データの品質）を最短で達成できる
- フラグ1つの変更なので、判断を誤っても戻せる
- データを消さないため、利用者が戻ってきたときに継続できる

### 5.4 削除を行う場合に必要な手続き
データの削除は、**実施前に以下を済ませておく必要がある**。

1. **利用規約への記載** … 保存期間と、期間経過後に削除し得ることを明記する
   （現在の利用規約には保存期間の記載がない）
2. **事前の告知** … 対象ユーザの登録メールアドレスへ通知する。
   メール登録率は約55%のため、**残り45%には通知が届かない**。
   ログイン時の画面表示も併用する
3. **猶予期間** … 告知から削除までの期間を置く
4. **削除の順序** … 論理削除（`DeleteFLG`）→ 一定期間後に物理削除。
   関連データ（`Member`・`Game`・`GameScene`・成績など）の整合を保つ順序で行う
