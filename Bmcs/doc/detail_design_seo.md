# 詳細設計書 - SEO（検索エンジン対策）

課題一覧の P-8（SEO 対策）と P-4（canonical がトップを指す）への対応をまとめる（2026-09-25）。
独自ドメイン（`bmcs.app`）への移行後に、検索エンジンからの集客の土台を作ることが目的。

## 1. 方針

- **検索結果に出すページを、各画面で明示的に指定する**（既定は `noindex`）。
  登録するページだけが `PageModelBase.SetIndex(ページ名, 正規URLのクエリ)` を呼ぶ。
  指定し忘れた画面は検索結果に出ない側に倒れる（ログインが必要な画面・アカウント復旧などが誤って出るより安全）
- **非公開チームの URL を検索エンジンに渡さない**。公開・非公開の判定は `PageModelBase.IsSearchTargetTeam` に1本化し、
  各画面の `noindex` とサイトマップの両方で同じ条件を使う
- 画面の見出し（h1）は変えず、検索結果・共有時のタイトル（`MetaTitle`）と説明文（`MetaDescription`）だけを画面ごとに固有にする

### 1.1 以前の問題（P-4）
`IsIndex` を立てていない画面は、canonical が**トップ**を指していた。
「トップと同じページ」と伝えることで検索結果から外す形になっていたため、
公開ページの `/Game/Details`・`/Privacy`・`/Term` なども、検索エンジンからはトップの重複として扱われていた。
一方、アカウント復旧の画面などは `IsIndex = true` で、検索結果に出る側になっていた。

## 2. 検索結果に出すページ

| 画面 | 条件 | 正規URL（canonical）に含めるクエリ |
| --- | --- | --- |
| トップ（`/`） | 常に | なし |
| 公開チーム一覧（`/Team/Index`） | 常に | `pageIndex`（2ページ目以降） |
| チーム情報（`/Team/Details`） | 検索対象のチーム | `id` |
| 試合一覧（`/Game/Index`） | 検索対象のチーム | `teamID`、`pageIndex`（2ページ目以降） |
| 試合結果（`/GameScore/Details`） | 検索対象のチームの**確定済みの試合** | `gameID` |
| イニング詳細（`/InningScore/Index`） | 同上 | `gameID`（イニング・表裏の絞り込みは含めない） |
| 成績（`/Score/Index`） | 検索対象のチーム、または公開チーム全体 | `scorePageClass`・`teamID`・`isPublic` |
| メッセージ（`/Message/Index`） | 公開メッセージの一覧のみ | `messagePageClass=Public`、`pageIndex`（2ページ目以降） |
| ユーザ登録・プライバシーポリシー・利用規約・お問い合わせ | 常に | なし |

**検索対象のチーム**（`IsSearchTargetTeam`）：公開・未削除・システムデータでない・サンプルデータでない。

- **成績の絞り込み（年・試合種別・カテゴリ・使用球・規定）、並べ替え、ページ送りは正規URLに含めない**。
  組み合わせの数だけ URL ができ、似た内容のページが大量に登録されるのを防ぐ
- 一覧の2ページ目以降は、1ページ目とは別の内容のため、それぞれを正規URLとする（1ページ目にまとめると、2ページ目以降のチームが見つからなくなる）
- 試合中・確定前の試合は、内容が変わり続け、成績にも集計されていないため登録しない

### 2.1 検索結果に出さないページ（判断が必要だったもの）

| 画面 | 理由 |
| --- | --- |
| メンバー一覧・メンバー情報（`/Member/*`） | **選手の氏名が検索でヒットするようになるため**。小学生などのチームもあり、本人・保護者が想定していない形で名前が検索結果に出るのは避ける（F-1 の顔写真の公開と同じ懸念）。成績の画面にも選手名は出るが、選手ごとのページは名前での検索に直結する |
| 試合情報詳細（`/Game/Details`） | 同じ試合の内容は試合結果の画面にまとまっているため（重複を避ける） |
| メッセージの返信（スレッド）・非公開・自チームの一覧 | 返信は内容の確認ができない利用者の投稿で、公開一覧から読めるため |
| サンプルデータのチーム（`YG`・`HT`） | 実在の球団名を使っており（P-1）、誰でも書き換えられる（D-10）。`SystemConstant.SampleDataTeamIDList` で指定する |
| トップのマイページ（`/Top/Index`） | ログインしているかで内容が変わり、未ログインでは案内だけになるため |
| アカウント復旧（6画面）・チーム作成・エラー・ログインが必要な画面 | 検索結果に出す意味がないため |

メンバーのページを登録するかは、**運営の判断で変えられる**（`Member/Index`・`Member/Details` で `SetIndex` を呼ぶだけ）。
変える場合は、利用規約・プライバシーポリシーへの記載もあわせて検討する。

## 3. 実装

### 3.1 head のタグ（`Pages/Shared/_HeadMeta.cshtml`）
- `IsIndex` のとき `<link rel="canonical">`、それ以外は `<meta name="robots" content="noindex">` を出す
  （noindex のページに canonical を出すと指示が矛盾するため、どちらか一方にする）
- `og:url` は、登録するページでは canonical と同じ URL にする
- 構造化データ（JSON-LD）を `<script type="application/ld+json">` で出す。
  利用者が入力したチーム名などに `</script>` が含まれても抜け出せないよう、`JavaScriptEncoder` で `<` などをエスケープする
- タイトルは `MetaTitle` → `ViewData["Title"]` の順に使う。説明文は `MetaDescription` → `ViewData["Description"]` → サービス全体の説明文（`SeoContent.SiteDescription`）

### 3.2 URL の基点（`Function/SiteUrl.cs`）
canonical・OGP・サイトマップ・robots.txt の絶対URLは、**設定値を優先**して組み立てる。
優先順：`Site:CanonicalHost`（`https://` を付ける）→ `EmailSettings:BaseUrl` → リクエストのホスト。
旧URL（`bmcs.azurewebsites.net`）や、書き換えられた Host ヘッダの URL を検索エンジンに伝えないため。

### 3.3 タイトル・説明文・構造化データ（`Function/SeoContent.cs`）

| 画面 | タイトルの例 | 構造化データ |
| --- | --- | --- |
| トップ | Bmcs - 草野球・ソフトボールのスコア管理・成績集計（無料） | `WebSite`・`WebApplication`（無料の `Offer`） |
| チーム情報 | 東京ベアーズ（東京都・社会人・軟式） | `SportsTeam`・`BreadcrumbList` |
| 試合一覧 | 東京ベアーズの試合一覧 | `BreadcrumbList` |
| 試合結果 | 2026/09/20 東京ベアーズ vs 横浜ドルフィンズ 試合結果 | `SportsEvent`・`BreadcrumbList` |
| イニング詳細 | 2026/09/20 東京ベアーズ vs 横浜ドルフィンズ イニング詳細 | `BreadcrumbList` |
| 成績 | 東京ベアーズの成績（投手）／公開チームの成績ランキング（野手） | `BreadcrumbList`（チームの成績のみ） |

- 説明文は 120 文字で切る（検索結果で省略されずに出るのはおおむねこの長さ）
- `SportsEvent` は、先攻をアウェイ（`awayTeam`）、後攻をホーム（`homeTeam`）とする。先攻後攻が未登録の場合は `competitor` に並べる
- 競技（`sport`）は、使用球がソフトボールなら `Softball`、それ以外は `Baseball`

### 3.4 パンくず（`Pages/Shared/_BreadcrumbTailwind.cshtml`）
`PageModelBase.BreadcrumbList` を画面に表示し、同じ内容を `BreadcrumbList` の構造化データとして出す。
「チーム一覧 ／ チーム名 ／ 試合一覧 ／ 2026/09/20 vs 相手 ／ イニング詳細」の形。
表示する画面：チーム情報・試合一覧・試合情報詳細・試合結果・イニング詳細・成績（チームを指定したとき）。

### 3.5 サイトマップ（`/sitemap.xml`、`Pages/Seo/Sitemap.cshtml.cs`）
2章の「検索結果に出すページ」の正規URLを、DB から自動生成する。
- 公開チームごとに、チーム情報・試合一覧・成績（4種類）
- 確定済みの試合ごとに、試合結果と、イニング詳細（「プレー毎」で入力した試合のみ）
- `lastmod`：試合は試合の更新日時、チームはチーム情報と試合の更新日時のうち新しいもの
- 条件は `IsSearchTargetTeam`・`IsSearchTargetGame` と同じ（SQL で書いているため、条件を変えるときは両方を直す）
- 1ファイル 50,000 件の上限を超える場合は新しい試合から載せる（現状の件数では届かない。超えそうになったら分割する）

### 3.6 robots.txt（`/robots.txt`、`Pages/Seo/Robots.cshtml.cs`）
- サイトマップの場所を絶対URLで書くため、静的ファイルではなく設定値から組み立てる
- `Disallow` は**ログインしないと開けない画面**（新規作成・編集・削除・スコア入力・管理者向け）に限る。
  `Disallow` にするとクローラが `noindex` を読めなくなり、URL だけが検索結果に残ることがあるため、
  検索結果から外す指定は `noindex` で行う

### 3.7 日本語のエンコード（`Program.cs`）
既定では Razor が ASCII 以外の文字をすべて `&#x8349;` の形で出力しており、日本語の多い画面ほど HTML が大きくなっていた。
`WebEncoderOptions` で全文字を許可し、日本語をそのまま出力する（`<`・`>`・`&`・`"` などは引き続きエスケープされる）。
主な画面で HTML が約6〜8% 小さくなった（ローカルで計測）。

## 4. 本番での作業（コードの外）

1. **Google Search Console にドメインを登録する**（ドメイン プロパティ `bmcs.app`）。
   所有権の確認は、Cloudflare の DNS に TXT レコードを追加する方法が簡単（http/https・サブドメインもまとめて確認できる）
2. サイトマップ `https://bmcs.app/sitemap.xml` を送信する
3. 「URL 検査」で、トップ・チーム情報・試合結果が「登録可能」になっていること、
   メンバー情報・アカウント復旧が「noindex で除外」になっていることを確認する
4. リッチリザルト テスト（https://search.google.com/test/rich-results）で、試合結果・チーム情報の構造化データにエラーが無いことを確認する
5. 旧URL（`bmcs.azurewebsites.net`）が検索結果に残っている場合は、301 転送により時間とともに新ドメインへ置き換わる（対応は不要）

## 5. 未対応（課題一覧 P-8 に残す）
- **公開ページの内容の充実**（成績・試合結果は表が中心で文章が少ない。直近の試合結果の要約、チーム紹介など）
- **表示速度の実測**（PageSpeed Insights。Core Web Vitals）
- GA4 の導入（P-3）と、検索での表示回数・順位の計測
- ランディングの見出し・本文の見直し（競合と比べて、検索で使われる語を調べてから）
