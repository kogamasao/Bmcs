**D-11 の検討事項（.NET 10 への更新）**
- 対象：`Bmcs.csproj` の `TargetFramework`（`net8.0` → `net10.0`）と、パッケージ（`Microsoft.EntityFrameworkCore.SqlServer`・`Microsoft.Extensions.Caching.SqlServer`・`Microsoft.AspNetCore.Identity.EntityFrameworkCore`・`Microsoft.EntityFrameworkCore.Tools`・`Microsoft.VisualStudio.Web.CodeGeneration.Design`）を 10 系へ
- **現在のパッケージは 8.0.0（初版）のまま**で、8.0.x のセキュリティ修正も取り込めていない。.NET 10 への更新までの間も、少なくとも 8.0 の最新パッチへ上げておくことが望ましい
- Azure App Service は、既存の Windows（F1）を切り替えるのではなく、**Linux の B1 を新規作成して .NET 10 で動かす**（P-6 の方針）。独自ドメインへの切り替えも同時に行う
- ローカルのビルド・実行環境（Docker の `mcr.microsoft.com/dotnet/sdk:8.0`、コンテナ `bmcs-app`）を 10.0 に
- EF Core 8 → 10 の破壊的変更の確認（特に `EnsureCreated`・生SQL（`ExecuteSqlRawAsync`）・LINQ の SQL 変換）、ASP.NET Core 9・10 の破壊的変更の確認
- 更新後は全画面の表示と、スコア入力〜確定・成績集計の一連の流れを確認する（ローカルのブラウザ確認の手順は今回の移行と同じ）

**D-9 の検討事項**
- 仮登録の間に何ができるか：本登録までログインさせないと、登録直後の離脱が増えるおそれがある（離脱分析では1日で離脱が118チーム）。
  「ログインや入力はでき、未確認の間は画面に案内を出す」形も含めて判断する
- トークンは `ResetToken` と同様に、ハッシュ化して保存し、有効期限を設け、1回で失効させる。再送には既存の送信回数制限（`SendMailLimitCount`）を使う
- 仮登録のまま期限が切れたアカウントの扱い（ユーザIDを解放するか）
- 既存ユーザ（メール未登録が約45%、登録済みも未確認）の扱い：ログイン時に確認を促すか
- チームのメールアドレス（チームパスワードの再設定に使用）も同じく未確認のため、同様の確認を行うか
- メールアドレス変更時（ユーザ情報編集）にも確認を行う

**M-20 の検討事項（打席後の記録の選択肢）**
- 原因：`PageModelBase.AfterDetailResultClassList` が、区分の値で「失策」以降（失策・補殺）に絞っている。打席中の選択肢（`BeforeDetailResultClassList`）はすべて選べる
- 対応：打席後の選択肢に **盗塁・盗塁死・WP・PB の4つを加える**（ボーク・牽制死は加えない）。区分の値の大小で絞る方式では表せないため、選択肢を明示的に列挙する形に変える
- 現状の回避方法：同じ内容を「打席中ランナー結果」に入れる。アウトの合計や成績は合うことが多いが、記録の順序（打者の結果より前に起きたことになる）が実際と違い、イニング詳細の表示も実際の流れと合わない。そもそも利用者がこの方法に気付けない
- 修正の見込み：成績の集計（`PageModelBase` の投手・野手成績）は、打席中・打席後を区別せず結果の種類（`DetailResultClass`）で数えているため、**選択肢を広げるだけで成績に反映される可能性が高い**。ただし次の確認が必要
  - 打席後の記録を前提にした処理（イニング詳細の文章の組み立て、ランナーの自動進塁、3アウトの判定、捕手の盗塁阻止の集計）に影響しないか
  - 同じ内容を打席中と打席後の両方に入れた場合の二重計上をどう防ぐか
- M-12（スコア入力画面の見直し）の「打席後ランナー結果が分かりにくい」とあわせて対応すると効率がよい

**M-12 スコア入力の分かりにくい点**（「プレー毎」は既定の入力方式で、今後改善していく方針。ui 7.5）
1. **オーダーが見えない**：打順・守備位置の一覧が画面に無く、打者はチーム全員（サンプルでは16人）のプルダウンから選ぶ。
   次の打者・現在の守備位置が分からず、誤選択しても気付きにくい。現在の打順（前後の打者）と守備位置を表示したい
2. **守備交代・選手交代が分かりにくい**：攻撃中の「守備」カードには相手投手の選択欄だけがあり、守備中は「守備」カードにボタンが出る。
   交代は別画面（打順設定の「選手交代」）で行うが、どこから何ができるのかが画面から読み取れない。代打・代走・投手交代・守備位置の変更を、それぞれ入口として示したい
3. **打席中ランナー結果の意味が分かりにくい**：盗塁・牽制死・暴投など「打席の途中に起きた走者の動き」を入れる欄だが、見出しだけでは伝わらない。
   ランナーがいるときだけ表示されるため、出たり消えたりする理由も分からない
4. **打席後ランナー結果が分かりにくい**
   - 1つのカードに、**相手の失策・補殺を記録する欄**（対象選手／結果）と**ランナーの進塁結果の表**が見出しなしで並んでいる
   - 結果の選択肢「得点(打無)」「得点(自無)」「得点(打自無)」が略語で、打点なし・自責点なしの意味が読み取れない
   - 打者結果に応じてランナーが自動で進塁するが、塁打分しか進まないため確認が必須。自動で動いたことが画面上で分からない
5. **塁上の状況が見えない**：走者の有無・誰がどの塁にいるかが、表の行を読まないと分からない。ダイヤモンド型の図で示したい
6. 画面上部の「戻る」「次へ」「最新へ」「元に戻す」「スキップ」の違いが画面から読み取れない（特に「スキップ」＝打順を1人飛ばす）
7. 関連：ヘルプ本文の整理（M-2）、2アウト時の警告（M-3）、コンテナ幅（M-11）

進め方の案：オーダー表示（1）と塁上の図（5）は表示の追加だけで済み、入力処理に触れないため先に着手しやすい。
2〜4 は入力データの構造（`GameSceneDetail`・`GameSceneRunner`）に関わるため、変更前に画面の流れを設計してから行う。

- 課金の例：広告を消す・通算成績（TeamHub）、高度な分析（SCORE BASE PRO）、**観戦者（家族）向けの閲覧（SCORE BASE・GameChanger）**。「チームは無料、観戦者が払う」形は、将来の収益化の参考になる

**F-11 の検討事項（直近○試合）**
- **「直近○試合」の数え方**：チーム成績・チームの試合単位では「チームの直近○試合」でよいが、個人成績では「チームの直近○試合」と「その選手が出場した直近○試合」で意味が変わる（控えの選手は、チームの直近5試合では出場が少なくなる）。どちらにするか、選べるようにするかを決める
- 全チームの集計（公開チーム成績）では、チームごとに直近○試合を取って合算する
- 年の絞り込みとの関係：直近○試合を指定したら年は無視するか、その年の中の直近○試合とするか
- **規定（試合数・投球回・打席）との関係**：試合数が少ないと規定に届かず一覧が空になりやすい。直近○試合の指定時は規定を外す、または規定を比例させる
- 試合の並び順：試合日の新しい順（同日は試合IDの順）。対象は確定済みの試合のみ（今の集計と同じ）
- 選択肢の例：5・10・20試合、または任意の数

**F-1 の検討事項（画像登録）**
- **保存先**：DB に入れず、Azure Blob Storage などに置く（DB の容量・バックアップの肥大化を避ける）。費用と、画像の配信方法（直接公開か、アプリ経由か）を決める
- **公開範囲とプライバシー**：公開チームの画像は誰でも見られる。**小学生などのチームもあるため、子どもの顔写真の公開**について、保護者の同意や、公開範囲の選択（チーム内のみ・公開）が必要か検討する。利用規約・プライバシーポリシーへの記載も必要
- **不適切な画像**：公開一覧に不適切な画像が載ると離脱につながる（D-3 と同じ懸念）。管理者が非表示・削除できる仕組み、通報の仕組みを用意する。体験用のサンプルチームでは登録できないようにする（D-10）
- **安全性**：ファイル形式を内容で確認する（拡張子だけで判断しない）、サイズの上限、画像を再エンコードして埋め込まれたスクリプト等を取り除く、**撮影場所（EXIF の位置情報）を削除する**
- **表示**：サムネイルの自動生成（一覧用の小さい画像）、未登録時の既定表示（頭文字など）、スマホからの撮影・アップロードのしやすさ
- **削除時の扱い**：チーム・メンバーを削除したとき、画像も消す

**P-6 の方針（2026-09-24 決定）**
- **現在の App Service は Windows の無料プラン（F1）で、独自ドメインを設定できない。** Windows の B1 は約10,300円/月と高いため、**Linux の B1（約2,200円/月、東日本）へ移行する**。DB は Azure SQL Basic（5 DTU、約850円/月）のまま
  - Linux への移行理由：ASP.NET Core はそのまま動き、ローカルの開発環境（Docker）がすでに Linux。B1 で独自ドメイン・無料のSSL証明書・常時起動（Always On）が使え、F1 の「CPU 1日60分」の制限もなくなる
  - DB の無料オファー（サーバーレス、月100,000 vCore秒）は採用しない：Bmcs はセッションも DB に保存しており毎リクエストで DB にアクセスするため、上限を超えやすい（超えると翌月まで停止か割高な課金）。停止明けの再開待ちも発生する
  - 見込み：**合計 約3,200円/月**（App Service 約2,200円＋DB 約850円＋ドメイン 年額の月割り）
- 既存の App Service の OS は変更できないため、Linux の App Service プランとアプリを新規作成し、アプリ設定（接続文字列・メール設定・Clarity 等）を移す。新しいアプリを azurewebsites.net の URL で確認してから独自ドメインを割り当てる
- **.NET 10 への更新（D-11）と同時に行う**（新しい Linux のアプリを最初から .NET 10 で作る）
- ドメイン候補（2026-09-24 の空き状況）：bmcs.com・.net・.org・.jp・.dev は取得済み。**第一候補 `bmcs.app`**（年2,000円前後の見込み。プレミアム価格でないか要確認。HTTPS 必須だが App Service の無料証明書で対応可）、第二候補 `bmcs-baseball.com`（年1,500円前後）。`.io` は高く、管理する地域の先行きも不透明なため避ける
- 取得先：**Cloudflare Registrar**（仕入れ値のまま・更新料も同額・WHOIS 代理無料）。初年度の安さではなく更新料で比べる。DNS も Cloudflare で管理し、App Service の証明書発行のため中継（プロキシ）は切った「DNS のみ」にする

**P-6 の検討事項（独自ドメイン）**
- 旧URL（`bmcs.azurewebsites.net`）からの 301 リダイレクト（検索エンジンの評価と、共有済みのリンクを引き継ぐ）
- canonical・OGP の URL を新ドメインにする。Google Search Console への登録とサイトマップ
- **パスワード再設定などのメールの送信元**を新ドメインにする場合は、SPF・DKIM・DMARC を設定する（迷惑メールに振り分けられないように）
- Clarity の対象URLの更新、GA4 の導入（P-3）

**P-8 の残り（2026-09-25 時点）**
- **公開ページの内容の充実**（下記の「公開ページの内容の充実」）
- **表示速度の実測**（PageSpeed Insights）
- 計測：Search Console（R-6）と GA4（導入済み）で、検索での表示回数・クリック・順位を見る
- ランディングの見出し・本文の見直し（競合と比べて、検索で使われる語を調べてから）
- **判断が必要**：メンバーのページ（選手の氏名）は noindex にした。検索に出す場合は利用規約・プライバシーポリシーへの記載もあわせて検討する（seo 2.1）
- サンプルデータのチーム（`YG`・`HT`）を検索対象から外し、公開チーム一覧・公開チーム全体の成績ランキングからも除いた（レビュー指摘で追加）。`HT`（阪神タイガース(サンプル)）は DbInitializer の初期データで、本番にも同じIDで存在する前提。違う場合は `SystemConstant.SampleDataTeamIDList` を直す

**P-8 の検討事項（SEO 対策）**（対応前の記録。実施内容は `detail_design_seo.md`）
- **現状（2026-09-24）**：title・description・canonical・OGP は `_HeadMeta.cshtml` で設定済み。**無いもの**：`robots.txt`、サイトマップ（`sitemap.xml`）、構造化データ（JSON-LD）、画面ごとの `noindex`、画像の代替テキストの整備
- **`robots.txt` と `noindex`**：ログインが必要な画面（試合入力・チーム情報変更・ユーザ情報・管理者画面など）と、検索結果に出す意味のない画面（アカウント復旧・再設定・エラー・お問い合わせの完了など）を除外する。`<meta name="robots" content="noindex">` はページ単位で確実に効く。`robots.txt` は Disallow だけでは検索結果から消えないため、noindex と使い分ける
- **サイトマップ**：公開チーム・チーム成績・試合結果・公開メッセージなど、公開画面の URL を自動生成する（`/sitemap.xml`）。公開・非公開（`PublicFLG`）と削除の状態を反映し、非公開チームの URL を載せない（漏えいの再発防止）。Search Console に登録する
- **canonical の見直し**：現在は `IsIndex = true` を立てていない画面の canonical がトップを指している（P-4 のとおり。`/Game/Details` など）。各画面が自分自身のURLを指すように直す。クエリパラメータ（並べ替え・ページ送り・絞り込み）の違いを、正規URLにまとめるか別ページにするかも決める
- **画面ごとの title・description**：チーム名・試合の対戦相手・年などを含めて、固有の内容にする（今は多くの画面が共通の説明文）。チーム一覧・成績は「草野球 ○○（地域）」など検索される語を含める
- **構造化データ**：チーム（`SportsTeam`）、試合結果（`SportsEvent`）、パンくず（`BreadcrumbList`）を JSON-LD で出力する。検索結果の見え方が良くなる
- **公開ページの内容の充実**：成績・試合結果のページは表が中心で文章が少ない。チームの紹介、直近の試合結果などの文章を増やす（F-4 のグラフとも関連）
- **表示速度・モバイル対応**（Core Web Vitals）：Tailwind への移行で軽くなったはずだが、実測（PageSpeed Insights）で確認する。画像を入れる場合（F-1）は遅延読み込みとサイズの最適化
- **リンク構造**：チーム一覧から各チーム・試合・成績へ、成績から選手へのリンクは既にある。パンくず（ホーム > チーム > 試合）を画面に出すと、利用者にも検索エンジンにも構造が伝わる
- **計測**：Google Search Console（検索での表示回数・クリック・順位）と GA4（P-3）を導入し、効果を測る
- ランディング（`/`）の見出し・文章に検索される語（草野球・ソフトボール・スコア・成績管理・無料）を自然に含める。競合（teams・TeamHub・スコアラー等）と比べて、検索で出てくる語を調べる

**P-9 の検討事項（AdSense の審査対策）**
- **独自ドメインが必須**（P-6）。取得したばかりのドメインは審査が通りにくい場合があり、公開して一定期間、内容を積み上げてから申請する
- **審査で見られる点**：①オリジナルの十分な内容（表だけのページ・ほぼ空のページは低評価）、②プライバシーポリシー・お問い合わせ・運営者情報が分かること、③サイトの目的と利用者が分かること、④ナビゲーションが分かりやすいこと、⑤ポリシー違反の内容が無いこと、⑥ログインなしで見られる公開ページが十分にあること
- **Bmcs 固有の懸念**
  - **ログインが必要な画面が多く、公開ページは成績・試合結果・チーム・メッセージが中心**。審査員が見られる公開ページが、体験用のサンプルチーム（架空のデータ）だけだと、内容が薄いと判断されるおそれがある。**公開チームの実データが十分にあるか**、と、ランディングや使い方の説明ページの充実が要る
  - **サンプルチームが実在の球団名**（読売ジャイアンツ等。P-1）。第三者の名称の不適切な使用と見られる可能性があるため、架空の名前に変える
  - **公開チーム一覧の質**（D-3・課題として挙げた不適切な公開データ）。低品質なデータが載っていると審査・広告主の双方に不利
  - **子どもの写真・個人情報**（F-1）：小学生チーム等の画像を公開する場合、ポリシーとプライバシーの両面で慎重に。子ども向けサービスの扱い（COPPA・広告の制限）にも注意
  - 利用規約・プライバシーポリシーに、広告配信事業者が Cookie を使うこと・オプトアウトの方法を書く（現在の記載は個人情報の取り扱いのみ）
  - Cookie 同意の扱い：日本向けが中心でも、EU からのアクセスがあれば同意管理（CMP）が要る場合がある。Google の要件を確認する
- 審査に落ちた場合の理由は AdSense の画面に出るので、それに沿って直す。落ちても再申請できる
- 広告を出す場所の方針は P-7 のとおり（操作画面には出さない）。`ads.txt`（広告の販売者の証明）の設置も必要

**P-7 の検討事項（広告）**
- 広告を出す場所：**スコア入力・試合結果の入力などの操作画面には出さない**（誤タップ・入力の妨げになる）。公開チーム一覧・成績・試合結果の閲覧画面を中心にする
- 表示の遅れ・画面のずれ（CLS）への影響。Clarity で離脱が増えないか確認する
- **プライバシーポリシーへの記載**（第三者の広告配信事業者が Cookie を使うこと、オプトアウトの方法）。AdSense の審査（独自の内容、プライバシーポリシー、お問い合わせの有無）
- 子ども（小学生チーム等）が見る可能性があるため、広告のカテゴリを制限する
- 体験用のサンプルチーム画面での扱い（新規訪問者の第一印象になる）
- 有料プランで広告を消す形（TeamHub と同じ）も、収益化の選択肢として合わせて検討する
