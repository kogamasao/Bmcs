# 詳細設計書 - UI（Tailwind CSS への移行）

## 0. 方針

UIが .NET Core の初期生成テンプレート（Bootstrap 4.3.1）のままで、新規ユーザへの訴求力が弱い。
また Bootstrap 4 はサポートが終了している。**Tailwind CSS 4 へ段階的に移行する。**

### 採用したもの

| 用途 | 採用 | 理由 |
| --- | --- | --- |
| CSS | Tailwind CSS 4（スタンドアロンCLI） | **単一バイナリで Node.js が不要**。生成CSSをコミットすればデプロイ手順が変わらない。配色・余白を自由に決められる |
| グラフ | Chart.js（導入予定） | 成績推移（折れ線）、選手比較（レーダー）、打球方向（散布図）が標準で揃う。canvas 1枚で動きビルド不要 |
| 図 | 手書きSVG（ライブラリなし） | ダイヤモンド図・ストライクゾーン図は、グラフライブラリより正確で軽量。Tailwind の `fill-*` / `stroke-*` で直接スタイリングできる |

**Bootstrap 5 への移行は採用しなかった。** 移行しても見た目は良くならず、`form-group`（190箇所）の
書き換えに対して、ユーザに見える改善がゼロだったため。

## 1. 構成

| ファイル | 役割 |
| --- | --- |
| `Bmcs/Styles/app.css` | Tailwind のソース。**配信されない** |
| `Bmcs/wwwroot/css/app.css` | 生成物。**リポジトリにコミットする** |
| `build-css.sh` | ビルドスクリプト（リポジトリ直下） |
| `Bmcs/Pages/Shared/_LayoutTailwind.cshtml` | Tailwind のみを読み込むレイアウト |
| `Bmcs/Pages/Shared/_HeadMeta.cshtml` | head内の共通タグ（旧レイアウトと共用） |
| `Bmcs/Pages/Shared/_HelpTailwind.cshtml` | ヘルプ（`<dialog>`。Bootstrap JS 不要） |
| `Bmcs/Pages/Shared/_PaginationTailwind.cshtml` | ページ送り。`PageHelper/PaginationInfo` を渡す |

`app.css` には、Tailwind の他に **`jquery-validation-unobtrusive` が動的に付与するクラス**
（`field-validation-error` / `input-validation-error` / `validation-summary-errors`）を定義している。
これらはHTMLに書かれないためTailwindの検出対象にならず、定義しないと入力チェックの表示が消える。

## 2. 移行手順

### 2.1 レイアウトを分ける理由
Bootstrap 4 と Tailwind は**同名で値が違うクラス**を持つため、1ページ内で併用すると崩れる。

| クラス | Bootstrap 4 | Tailwind |
| --- | --- | --- |
| `container` | max-width 540〜1140px、左右padding、中央寄せ | max-width がブレークポイント幅、paddingなし |
| `mb-3` など | 1rem | 0.75rem |
| `table` | width・余白・文字色 | `display: table` |

そのため、**ページ単位でどちらか一方だけを読み込む**。

- 未移行の画面 … `_Layout.cshtml`（Bootstrapのみ）※`_ViewStart.cshtml` の既定
- 移行済みの画面 … `_LayoutTailwind.cshtml`（Tailwindのみ）※ページ側で `Layout` を指定

**この方式の弱点**：ヘッダーが2つになるため、リンクを写し漏らすと
「画面によって到達できる機能が変わる」という機能の欠落が起きる。
実際に初回の実装でユーザ情報・公開チーム成績・管理者メニューが丸ごと抜けていた。

そのため、**移行の受け入れ条件を「旧レイアウトとのリンク差分がゼロであること」**とする。
確認方法（管理者でログインした状態で実行する）:

```sh
# 移行済みページと未移行ページで、ヘッダーのリンクが一致することを確認する
curl -s -b cookie.jar http://localhost:15080/Top/Index  | grep -oP '<a class="rounded-md[^>]*href="\K[^"]+' | sort -u
curl -s -b cookie.jar http://localhost:15080/Game/Index | grep -oP '<a class="nav-link[^>]*href="\K[^"]+'  | sort -u
```

プレフィックス（`tw-`）を付けて共存させる方法もあるが、全クラスが冗長になり、
移行完了後に外す作業が発生するため採用しない。

### 2.2 移行の順番
1. **ランディングページ（`/`）** ← 完了。新規訪問者が最初に見るため最優先
2. 共通レイアウト（ヘッダー・フッター） ← `_LayoutTailwind.cshtml` として作成済み
3. **トップページ（`/Top/Index`）** ← 完了。ログイン直後に必ず通るため
4. **新規登録の導線（`/UserAccount/Create`・`/Team/Create`）** ← 完了。
   離脱分析で、1日離脱の54%がこの2画面より前で止まっていたため優先した
5. **メンバー（一覧・追加・編集・削除・詳細の5画面）** ← 完了
6. **試合一覧・試合作成（`/Game/Index`・`/Game/Create`）** ← 完了
7. **打順設定（`/Order/Edit`）** ← 完了
8. **スコア入力（`/GameScene/Edit`）** ← 完了
9. **試合結果（`/GameScore/Edit`・`/GameScore/Details`）** ← 完了
10. 成績 → メッセージ → チーム → 管理系 → …
   ※ランディングに載せるスクリーンショットは、スコア入力と成績の移行後に撮影する
11. Bootstrap と `site.css` を削除

### 2.3 移行完了時に対応が必要なもの
- **ナビの開閉とモーダル**（`data-toggle` 4箇所）… Bootstrap の JS を外すと動かなくなる。
  `_LayoutTailwind.cshtml` のスマホメニューは `<details>` で実装し、JavaScript不要にしている
- **jQuery は残す**… `jquery-validation-unobtrusive` が依存しているため。外すと入力チェックが動かない
- `html { font-size: 14px }`（`site.css`）… Tailwind は 16px 前提。移行済み画面では `site.css` を読まないため影響しない

## 3. ランディングページ（`/`）

### 3.1 変更前の問題
- **ログインフォームが最上部にあり、未登録の訪問者が最初に入力欄を見る**構成だった
- 「未対応事項」が赤枠で目立つ位置にあり、登録前に不安を与えていた
- `landing-itemization-ul` が `height: 400px` 固定で、内容量に対して余白が不揃いだった
- 見出しが `display-3` / `display-5` / `landing-font` など独自クラスで乱立していた

### 3.2 変更後の構成
| 順番 | 内容 |
| --- | --- |
| 1 | ヒーロー：左に価値の説明とCTA、**右にログインカード** |
| 2 | できること（4枚のカード） |
| 3 | 体験への導線（濃色の帯） |
| 4 | できないこと（琥珀色。赤より落ち着いた配色にした） |
| 5 | よくあるお問い合わせ（`<details>` による開閉。JavaScript不要） |

**ログインを右カードに残した理由**：既存ユーザは毎回ここからログインするため、
下げると日常利用の妨げになる。新規訪問者は左の説明を読み、既存ユーザは右上のカードを使う。

### 3.3 サンプルログインの改善
「サンプルチームで体験する」ボタンは、以前は**ログインフォームまでスクロールするだけ**で、
訪問者が画面に表示されたID・パスワードを手で入力する必要があった。
`wwwroot/js/index.js` でID・パスワードを自動入力して送信し、1クリックで体験できるようにした。

## 4. トップページ（`/Top/Index`）

### 4.1 変更前の問題
- 機能への導線が**縦一列の全幅ボタン**で、何の画面かは名前からしか分からなかった
- 未ログイン時の案内が赤（危険色）で、制限の説明としては強すぎた

### 4.2 変更後
- 機能への導線を、アイコンと短い説明を添えた**タイル**にした
- お知らせ・最新メッセージを右カラムにまとめた
- 未ログイン時の案内を琥珀色にし、ログインとユーザ登録の両方を並べた
  （未ログインの訪問者は、まだユーザを持っていない場合がある）

## 5. 離脱分析の結果（2026-09-21）

本番DBを集計した結果（`doc/query/20260921_churn_analysis.sql`）。
**UIの改善順序は、この結果に基づいて決める。**

| 継続期間 | チーム数 |
| --- | --- |
| 1日未満 | 118 |
| 1週間未満 | 23 |
| 1ヶ月未満 | 13 |
| 半年未満 | 18 |
| 半年以上 | 33 |

1日で離脱した118チームの到達段階：

| 到達段階 | チーム数 | 平均選手数 | 平均プレー数 |
| --- | --- | --- | --- |
| ① チームを作っただけ（選手登録なし） | 43 | 0 | 0 |
| ② 選手は登録したが、試合を作っていない | 21 | 14 | 1 |
| ③ 試合は作ったが、打順を組んでいない | 16 | 23 | 0 |
| ④ 打順は組んだが、スコアを1球も入れていない | 3 | 13 | 0 |
| ⑤ 1試合は入力したが、2試合目がない | 23 | 22 | 37 |
| ⑥ 2試合以上入力した（それでも離脱） | 12 | 20 | 66 |

入力方式別の離脱率：**試合結果のみ 33%（13/39）／プレー毎 50%（54/109）**。
ただし継続チームのうち「試合結果のみ」を使う26チームは平均37試合を入力しており、
**「試合結果のみ」は初心者向けの妥協ではなく、長く使われている本線**である。

### 分かったこと
- **打順画面そのものは壁ではなかった**（④はわずか3チーム）
- 最大の塊は①の43チーム。チーム作成直後に離脱している
- ②③の37チームは平均14〜23人の選手を登録した**うえで**離脱している。意欲は高い
- ⑤⑥の35チームは1試合を完走してから戻ってこない。**UIではなく再訪の問題**

### ③の原因（実装の不具合。修正済み）
1. 試合を作成すると自動で打順設定画面へ遷移する（`Game/Create.cshtml.cs`）
2. **試合一覧には「打順設定」への導線が無く**、試合前の試合には
   「試合情報編集」「削除」しか表示されていなかった
3. 打順未設定のまま `GameScene/Edit` を開くと、投手の打順を参照する箇所で
   NullReferenceException となり**500エラー**になっていた

つまり打順画面から離脱した時点で、その試合のスコア入力に到達する手段が無かった。

### 未確定（Clarityで確認する）
①②が「項目数が多くて諦めた」のか「次の操作が分からなかった」のかは、
このデータでは判別できない。録画で確認してから改修する。

## 6. 新規登録の導線（`/UserAccount/Create`・`/Team/Create`）

### 6.1 ヘルプの置き方を変えた
従来は各画面の「？」ボタンでモーダルを開く方式だった（`_Help.cshtml`）。
説明の内容自体は十分に書かれていたが、**モーダルはフォームを覆うため、
読みながら入力できない**。また小さなアイコンを能動的に押す必要があり、
入力中のユーザは開かない。

そのため移行済みページでは、
- **各項目の要点は入力欄のすぐ下に直接書く**（1〜2行）
- 操作手順などの詳しい説明は「この画面の使い方」ボタンに残す（`_HelpTailwind.cshtml`）

`_HelpTailwind.cshtml` は `<dialog>` を使用し、Bootstrap JS と jQuery に依存しない。
本文は管理者が登録したHTMLのため、`@@plugin "@@tailwindcss/typography"` の
`prose` クラスで表示する。

### 6.2 チーム作成の変更
必須は5項目（チームID・チーム名・チーム略名・パスワード・確認用パスワード）だが、
13項目すべてが必須に見える状態だった。

| 変更 | 理由 |
| --- | --- |
| 任意8項目を折りたたみに入れた | 実際の2.6倍の重さに見えていた |
| 並び順を チーム名 → 略名 → チームID → パスワード に変更 | チームIDが1項目目にあり、最初の入力が正体不明の識別子だった |
| チームIDに説明を追加 | **チームメイトが参加するときに使うID**で、あとから変更できないことが書かれていなかった |
| 略名をチーム名から自動補完（`wwwroot/js/team-create.js`） | 手入力を減らす。ユーザが自分で編集した後は上書きしない |
| 公開設定に説明を追加 | 何が公開されるのか分からないまま判断させていた |

### 6.3 チーム作成後の遷移先を変更した
従来はチーム作成後にトップページへ遷移していたが、**選手登録画面へ直接進める**ようにした。
1日で離脱した118チームのうち**43チームが選手を1人も登録していない**（最大の塊）ため、
次にやることを画面で示すのではなく、そのまま次の作業に入れる形にした。

### 6.4 2カラムの高さずれ
説明文を入力欄の上に置いたため、左右で説明の行数が違うと入力欄の高さがずれていた。
`grid-rows-subgrid` で「ラベル／説明／入力欄」の各行を左右でそろえている。

**外側グリッドには `sm:gap-y-0` が必須。** `gap` はsubgridの行間にも適用されるため、
付け忘れるとラベル・説明・入力欄の間に余分な空きができる。
行間は各要素の `mt-*` で取る。

※subgrid 未対応のブラウザでは従来どおり（ずれるだけで、崩れはしない）

### 6.5 ユーザ作成の変更
**チーム選択のプルダウンをテキスト入力に変更した。**
従来は `PageModelBase.TeamIDList` で**削除以外の全チーム**を列挙していたため、
未ログインのユーザ作成画面に**非公開チームのチーム名とIDまで表示されていた**。
参加する人はチーム代表からIDを聞いているため、入力欄で足りる。

あわせて、参加時のエラー文言を
「パスワードが間違っています。」→「チームID、またはチームパスワードが間違っています。」
に変更した（チームの存在有無を判別させないため、両方で同じ文言とする）。

### 7.3 編集・削除・詳細
| 変更 | 理由 |
| --- | --- |
| 編集の入力エラーで500になる問題を修正 | `ModelState` が不正なとき `Member.Team` を取り直さずに `Page()` を返しており、画面でチーム名を参照する箇所で例外となっていた（追加画面と同じ原因） |

### 7.4 成績テーブルの共通スタイル
列数が多く横スクロールする表は、**セルごとにユーティリティを並べると1ファイルに
100箇所以上必要になる**ため、`app.css` にコンポーネントとして定義した。

| クラス | 役割 |
| --- | --- |
| `.stat-table` | 列数の多い成績表。ヘッダを縦スクロール時に固定する |
| `.col-fix-left` | 横スクロール時に左端の列を固定する（どの行か分からなくなるため） |

旧 `customize.css` の `.column-fix-left`（5ファイル・52箇所）に相当する。
**成績画面の移行でもこの2クラスを使う。**

**選手の一括登録は未実施**（全画面リニューアル後に実施する方針。8章参照）。

## 7.6 打順設定（`/Order/Edit`）

| 変更 | 理由 |
| --- | --- |
| **初回は登録済みの選手を背番号順に自動割当** | 2試合目以降は前回オーダーを引き継ぐが、初回は9枠すべてが空で、9回の選択を求めていた。対象は「選手」と「選手兼監督」 |
| 自動割当したことを画面に表示 | 勝手に入っていると誤解されないよう、「必要なところだけ変更してください」と添える |
| 「オーダー追加」→「打順を追加」 | 何が追加されるのか分かりにくかった |
| 登録ボタンを「この打順で始める」 | 保存後にスコア入力へ進むことが分からなかった |
| 「戻る」→「試合一覧へ」「スコア入力へ戻る」 | 遷移先が分からなかった |

### JavaScript の変更（`wwwroot/js/order.js`）
この画面は行の追加・削除・添字の振り直しをJSで行っており、**Bootstrapへの依存が2つ**あった。

| 依存 | 対応 |
| --- | --- |
| エラー表示の `d-none`（Bootstrapのクラス） | Tailwind の `hidden` に変更（6箇所） |
| 試合中の打順追加が Bootstrap のモーダルAPI（`.modal('hide')`） | `<dialog>` に置き換え、開閉処理をJSに追加 |

**JSフック（`js-rename` など81箇所）はすべて維持している。** 行のクローンで添字を振り直す仕組みに手を入れると壊れるため、クラス名は変更していない。

## 7.7 スコア入力（`/GameScene/Edit`）

554行・入力の中核となる画面のため、**構造は変えずクラスの置換に留め**、
必要な追加のみ行った。

| 変更 | 理由 |
| --- | --- |

### 発見した既存バグ（修正済み）

## 9. 入力エラー時の再表示について（移行時の必須チェック）

**`ModelState.IsValid == false` で `return Page()` する箇所は、画面が参照する
関連データを取り直しているか必ず確認する。**

取り直していないと、
- ビューがナビゲーションプロパティ（`Game.Team.TeamName` など）を参照していれば **500**
- ヘルプ（`SystemAdmin`）を参照していれば**ヘルプボタンが消える**

実際に `Member/Create`・`Member/Edit`・`Game/Create`・`Game/Edit` の4画面で
500が発生していた（いずれも修正済み）。対処は `SetPageDataAsync()` を用意して
`return Page()` の前に呼ぶ形で統一している。

### 未対応（各画面の移行時に対応する）
入力エラー時にヘルプが消える画面。500にはならないが、
**ユーザが最も困っている瞬間にヘルプが消える**。

`Order/Edit`・`GameScene/Edit`・`GameScore/Edit`・`Team/Edit`・`UserAccount/Edit`・`Message/Index`

※`Team/Create`・`UserAccount/Create`・`Inquiry/Create` は対応済み。

## 10. デザインの決めごと（移行時に守る）

レビューで「同じ操作なのに色やサイズが違う」指摘が出たため、方針を明文化する。

### 10.1 ボタンの色
| 色 | 用途 |
| --- | --- |
| `bg-emerald-700` | **新規作成・保存**（前進する操作）。1画面に1つまで |
| `bg-sky-700` | 参照・移動のうち、特に目立たせたいもの |
| `border-slate-300 bg-white` | 副次操作（キャンセル・一覧へ戻る・別画面への移動） |
| `bg-red-600` | 破壊的操作の実行（削除の確定） |
| `border-red-300 text-red-700` | 破壊的操作への入口（一覧の「削除」） |

**`emerald-600` は使用しない。** 白文字とのコントラストが 3.65:1 で WCAG AA（4.5:1）を
満たさないため。`emerald-700` は 5.36:1。同様に `emerald-500`（2.47:1）も白文字では使えない。

### 10.2 文字色
| 色 | 白背景 | slate-50/100 の上 |
| --- | --- | --- |
| `text-slate-600` | 7.58 ✓ | ✓ |
| `text-slate-500` | 4.76 ✓ | 4.35 ✗（`slate-100` 上では使わない） |
| `text-slate-400` | 2.63 ✗ | ✗ |

### 10.3 ボタンの大きさ
| 段 | クラス | 用途 |
| --- | --- | --- |
| 大 | `px-6 py-3` | フォームの送信 |
| 中 | `px-5 py-2.5 text-sm` | 画面内の遷移 |
| 小 | `px-3 py-2 text-xs` | 表の行アクション |

### 10.4 コンテナ幅
- フォーム … `max-w-2xl`（項目が多い場合は `max-w-3xl`）
- 一覧・詳細 … `max-w-6xl`

### 10.5 ヘッダメニュー
**リンクの定義は `PageModelBase.GetHeaderLinkList()` / `GetHeaderAccountLinkList()` に1本化する。**
レイアウトが2つある間にリンクを別々に書くと片方だけ写し漏れる（実際に発生した）。
レイアウト側は見た目だけを担当する。

## 11. 制約事項・未対応

- 全画面の移行は未完了（現在はランディングページとトップページのみ）

  匿名で閲覧できる公開ページのうち、該当するのは **`/Game/Details`（試合情報詳細）** のみ

- **計測ツールが未導入**。訪問数・流入元・CTAのクリック状況が一切取得できていないため、
